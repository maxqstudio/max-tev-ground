# Security and research boundaries

- MAX Research Ground is a local research application. It does not place, route, or manage live trades.
- The prior `D:\MAX_JEV_BENCHMARK\JEV_TEV_EURUSD_H1_LAST2M` research project is outside this repository. The importer and acceptance runner do not read, copy, or modify it. No host-side baseline check is claimed in GitHub evidence.
- The Tauri shell exposes a native file picker and narrow source-inspection, preview, confirmation, cancellation, catalog, and integrity-inspection commands. The frontend receives an opaque selection token rather than an arbitrary filesystem path. Source data remains local and is copied only into the application's dataset staging area after selection.
- The store rejects symlinked storage directories and database files, verifies source and staged files, enforces byte and row quotas, and promotes a complete snapshot before registering it. Failed and cancelled imports do not create registered datasets. The application does not expose a general filesystem, process, shell, credential, or arbitrary network command.
- SQLite stores experiment and dataset metadata, fingerprints, provenance, import attempts, and immutable registry state. Database triggers prevent metadata edits/deletes; each catalog read rechecks the manifest SHA-256 and raw/Parquet snapshot hashes. Hashes detect content changes; they are not signatures against an actor able to rewrite the database and all related files.
- GitHub Actions uploads a source-SHA-bound acceptance summary and checksum; the default-branch workflow signs the report. Build and test steps do not receive attestation write permissions.
- No runtime secret, MT5 account bridge, or trading API is configured. The only model endpoint is the Owner-configured loopback Ollama address described below. The future MT5 bridge must remain read-only and separately accepted before any terminal interaction is claimed.
- Repository fixtures are labeled synthetic parser-test data. They are not historical market data, trading results, or acceptance benchmarks. No synthetic market bars are generated during import.
- Feature Studio reads only registered datasets through the dataset store. It has no file picker or path-taking command. Before computing, it re-verifies each input and recomputes the canonical row fingerprint from the bytes it reads; after computing, it re-hashes the source. Inputs that are not `READY`, are tampered, or are missing are refused. After registration, every catalogue read and the downstream output accessor re-verify each source snapshot's bytes and canonical hashes, so tampering with a source revokes the feature set's `READY` status. Feature outputs are staged in a private directory, journaled, and promoted atomically; recovery preserves mismatched evidence and fails closed. These checks detect accidental or out-of-band changes; they are not signatures against an actor able to rewrite the database and every related file.
- The Strategy Engine (RG-R03) reads only registered feature sets through the feature store. It has no file picker or path-taking command, and its requests reject unknown fields such as order sizes. It evaluates a private, digest-verified copy of the feature output and recomputes the feature row fingerprint while deciding. Every catalogue read re-verifies the consumed feature set and, through it, the source datasets, so tampering anywhere upstream revokes a decision set's `READY` status. Decisions are research records: no order, broker, MT5, or account interface exists.
- A database schema upgrade never runs without a verified, consistent backup of the existing store in `schema-backups/` beside it. If the backup cannot be written or verified, the application does not upgrade the store and does not start. Each backup has a checksum receipt written when it is taken, and a restore accepts only a backup that still matches its receipt. The receipt detects changes to the backup alone; it is not a signature against someone who can rewrite both files. A restore never deletes the files it replaces, and a failed final check puts the original files back. Backups hold the same research metadata as the database and stay on the local machine.
- Keep credentials out of manifests, logs, screenshots, and commits. Further model adapters, external connections, or trading integrations require their own threat review and scoped capabilities.
- Dependencies are exact-pinned and lockfiles are committed. Report security issues to the Owner before publishing changes.

## RG-R04 model adapter threat review

Model Lab (`rg-model-registry`) adds two adapters. This review covers what each can reach and what fails closed.

- **Network reach.** The Ollama endpoint must be `http://` followed by a literal loopback IP (`127.0.0.0/8` or `[::1]`) and a port. Host names, including `localhost`, are refused, so name resolution or a hosts-file entry cannot redirect a request off the machine. Credentials, paths, queries, and `https://` are refused. The client is a minimal HTTP/1.1 implementation with no proxy support.
- **Permitted calls.** The client can make only `GET /api/version`, `GET /api/tags`, and `POST /api/generate`. Pull, push, create, copy, delete, blob, show, embedding, and process-control endpoints cannot be expressed; tests show they are refused before any connection is opened. Redirects are reported and never followed.
- **Response bounds.** Every request has a total deadline. Headers are limited to 16 KiB, listings to 1 MiB, and generations to 256 KiB, whether the length is declared or chunked. Compressed or unknown transfer encodings are refused.
- **Runtime control.** The application never starts, stops, signals, or downloads into a runtime. Cancellation stops reading between rows, and a timeout closes only the application's own socket.
- **Prompt contents.** A prompt holds the Owner's instruction and the bound input names and values of one row. No timestamps, symbols, timeframes, or row positions are included, so a language model cannot be told which date it is evaluating and recall what followed it from training data.
- **Model output.** Answers are parsed as data and checked against the declared schema: exactly the declared fields, finite numbers inside declared bounds, and declared labels only. Anything else is recorded as `INVALID_OUTPUT` with no value. Model text is never executed, rendered as HTML, or used as a path or command.
- **ONNX files.** A selected `.onnx` file is copied once into private storage, size-limited (256 MiB by default) and hashed. The original is not read again. The file is decoded by a strict, bounded protobuf reader. External tensor data (a path inside the model), model-local functions, subgraphs, sparse and training data, and other domains are refused rather than skipped, so a model can never cause a file read. The built-in interpreter evaluates only the listed operators and checks node count, parameter count, tensor sizes, and per-row operation count before the model can be registered or run. No native inference library, execution provider, or `unsafe` code is involved.
- **Identity and drift.** A model is registered only after explicit confirmation of the identity the Owner previewed. Its identity binds the content digest: the Ollama manifest digest or the SHA-256 of the copied ONNX file. A changed ONNX file, or a runtime that now reports a different or missing digest, quarantines the model; it is never silently re-identified. An unreachable runtime is reported as `RUNTIME_UNAVAILABLE`, never as model output.
- **Authority.** Every model output is `ADVISORY_ONLY`. Requests for decision filter, veto, override, position sizing, or order generation are refused. Inference reads decision sets but never writes them, and no order, broker, or MT5 interface exists.
- **Inputs and records.** Inference reads only `READY` feature and decision sets through their stores' downstream boundaries. The bytes read are a private digest-verified copy, and the upstream row fingerprint is recomputed while reading. Inference records are staged, confirmed, journaled, and promoted atomically. Every read re-verifies the record, its input, and its model registration. Hashes and receipts detect accidental or out-of-band changes; they are not signatures against an actor able to rewrite the database and every related file.
- **Tests.** CI and the acceptance runner use a loopback mock runtime and labeled synthetic ONNX fixtures only. No real model runtime, model download, or external network is used, and fixture outputs are not evidence of model quality.
